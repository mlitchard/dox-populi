  # Let's Play Screeps (Part 1)

  Screeps is a tower defense game that takes commands from players programming
  JavaScript.
  Each dox-populi tutorial is modeled after the original screeps
  [tutorial](https://github.com/screeps/tutorial-scripts).
  Along the way, you'll work your devflow muscles by familiarizing yourself
  with the process of creation, verification, and deployment.
  By the end, you'll have a colony running, ready to be improved and extended.
  The first tutorial will get you started with dox-populi.

  You'll get a Screeps colony to play with and exercises to test
  your understanding and the project's premise: Can the LLM
  use the structure of the project to facilitate productivity with
  tools that would otherwise be out of reach?

  ## The shape

  In the VM:

  - dox/creeps.dox — the klanker-written spec. Paradox
    checks the spec for internal consistency. Only validated specs
    generate TypeScript.
  - harness/main.ts and harness/role.harvester.ts — the TypeScript
    harness that makes the game calls, using that generated logic.
  - a game server and a browser viewer.
  - an install of [detnix](https://docs.determinate.systems/), with
    various tooling available in the devShell.

  ## By the end you will have:

  - Edited every layer of the stack — the spec
    ([dox/creeps.dox](https://gitlab.com/dox-populi/screeps/-/raw/tutorial-one/d
  ox/creeps.dox)),
    the [TypeScript 
  harness](https://gitlab.com/dox-populi/screeps/-/tree/tutorial-one/harness),
    the [tutorial's JS](https://gitlab.com/dox-populi/screeps/-/tree/tutorial-on
  e/tutorial-js/section1)
    — and pushed each change through the deploy pipeline.
  - Investigated a live server using the viewer, its console, and
    [room-feed](https://gitlab.com/dox-populi/screeps/-/blob/tutorial-one/room-f
  eed.sh).

  ## Start

  If you have not installed dox-populi yet, follow the
  [README](https://gitlab.com/dox-populi/screeps/-/blob/main/README.md).

  ## How the lesson works

  Every exercise runs the same loop: write down what you expect before
  you run anything, run it, then hold the room against your notes. The
  exercises are placed so that by the time one asks for a prediction,
  the material to make it is already on your screen — a file you just
  read or a room you just watched.

  [Before you begin](exercises/before-you-begin.html) sets up your
  environment and the working method: your agent's answers are claims,
  the instruments in the flake produce the evidence, and you decide.
  Read it before the first exercise.

  ## The plan

  1. [The walk](#the-walk) — server, client, deploy pipeline. Three
     exercises live on the walk, each at the moment its subject is on
     screen.
  2. [The exercises](#the-exercises) — six edits to the program, each
     held against your predictions.
  3. [The close](#the-close) — the original tutorial held against the
     port.

  # The walk

  ## The server

  `nix run .#server` starts the open-source Screeps server.

  **Get in the mix — [refactoring](mix/local.html).** Two of the
  flake's apps, `reset-local` and `stop`, do nearly the same job. Read
  both in flake.nix, then file the issue their similarity calls for:
  one parameterized script, `nix run .#local -- reset` and
  `nix run .#local -- stop`. The stretch goal is taking the issue and
  delivering.

  ## The client

  The browser client has several features. First is the map on the
  left, and the metadata panel on the right. Below that you'll find two
  tabs: the console and the code delivered from the client generator.

  **Get in the mix — [the client](mix/client.html).** The viewer is
  part of this repo: plain TypeScript in `viewer/src/`. Add a creep
  counter to the top bar: find where a room frame arrives each tick,
  count the creeps in the room state, and set your counter from that.
  The viewer's own tsc gate checks the change, and the running room
  witnesses it when a creep spawns or dies.

  ## The deploy

  `nix run .#deploy-local` reads
  `dox/creeps.dox`, Paradox verifies the spec's named properties and
  generates the decision logic, tsc typechecks the harness against
  that generated code, and the bundles land on the server as `main.js`
  and `role.harvester.js`.
  From then on the server calls that code every tick. The files you
  can read — the spec and the harness — are now the only player in the
  world.

  **Get in the mix — [breaking things](mix/break.html).** You just
  read what the pipeline checks; now trip both gates on purpose.
  Remove a body part the spec still uses, write down what
  `paradox check` will say, and compare its rejection to your note.
  Then give the harness a role the spec never declared and do the same
  with the build. The stretch goal is a change both gates accept,
  landing in the world.

  # The exercises

  The promise of the new technology is one of access and velocity.
  However we are still required to keep our hands in the code, which I
  believe the klanker makes possible in a way that lets us confront
  code and systems we might otherwise be unable to manage in a
  productive way. Bring your curiosity and bravery to these exercises
  and have fun with the process.

  Six exercises, in order — the source line you find in the first one
  comes back in the last. Each names what it needs deployed and gives
  the command.

  **[Picking a source](exercises/0-sources.html)** — Your room has two
  sources, and each program picks one differently: the tutorial JS
  takes `sources[0]`, the port measures path distance from where the
  creep stands. `room-feed` prints the sources in the server's own
  order; do the distance arithmetic by hand, predict where each
  program sends its creep, then watch both walks.

  **[Turn-around threshold](exercises/1-turn-around.html)** — The
  harvester turns for home on one condition, and it sits in the
  harness in both worlds. Change it to turn around at half-full. Both
  gates pass — the threshold is a number, and a different number is
  still well-typed. The check you work out by hand before deploying is
  the only test of the change, and the exercise ends in
  `tests/integration.nix`, where that same check reads `Memory.trace`
  as an assertion.

  **[Same mistake, two worlds](exercises/2-same-mistake.html)** — One
  typo, made twice: `getFreCapacity` in the tutorial JS, `wrok` in the
  spec. Before each deploy, write down when the report will arrive,
  where you'll read it, and what it will name. The console tab, the
  terminal, and the viewer hold the answers.

  **[The 1500-tick funeral](exercises/3-funeral.html)** — Every creep
  dies of old age at 1500 ticks, and the panel counts it down. You've
  read both worlds' main files; answer on paper what each room looks
  like at tick 1600, then watch a funeral in each world and find the
  lines in `harness/main.ts` that account for the difference.

  **[Memory leak autopsy](exercises/4-memory-leak.html)** — The port's
  harness opens with a cleanup loop that deletes dead creeps from
  `Memory.creeps`. Remove it, write down what the ledger and the
  panel's byte count will do as creeps die and are replaced, then
  retire a few harvesters and hold both against your notes. Both gates
  pass here too.

  **[The second harvester](exercises/5-second-harvester.html)** — Add
  a second creep to each world. In the JS world growth costs a console
  command; in the port it is a policy line in `harness/main.ts` you
  edit. Predict when the second creep appears and where each pair ends
  up — the source line from the first exercise answers from each
  creep's own position.

  # The close

  **[Concluding](mix/concluding.html)** — the original tutorial held
  against the port. Wipe the world, deploy the tutorial's own JS,
  write down how long the colony keeps working, and watch until the
  room goes still. Then sort the tutorial's statements into decisions
  and actions and check each column against the port — it is the
  answer key. The last stop is klanker slop in `vm/module.nix`,
  cleaned by hand.

● Note saved. Here's the analysis of the two orders.

  Server → Client → Deploy (client section stops before login; login finishes in
  the deploy section)

  Pros: the reader gets a picture early — start the server, open the viewer, see
  the world before any pipeline text. That's the natural first instinct and the
  gentlest opening.

  Cons: the client section can only show half its subject. It stops before
  login, and the two tabs it introduces hold their content only after a deploy —
  the console has nothing to talk to and the code tab has nothing delivered.
  The counter exercise has the same problem at its station: its verification
  step is watching the count move when a creep spawns or dies, and there's no
  creep until the deploy lands. So the section splits across the deploy section
  and the exercise's payoff is deferred — which is the confusion you flagged.

  Server → Deploy → Client

  Pros: the client section arrives whole. Login is done, code is on the server,
  both tabs are live, and the panel has a creep in it. The counter exercise
  verifies in place at its own station. The anamnesis fit is also better: the
  deploy section states that the server calls the deployed code every tick, and
  the client section is where the reader watches that claim hold — the deploy
  text supplies the prediction, the viewer supplies the evidence.

  Cons: two terminal-only sections back to back before the reader sees anything.
  And the breaking-things exercise sits at the deploy station before the reader
  has watched a healthy room: its two gate-trips read fine on the terminal, but
  its stretch goal (deploy the second work part, retire the creep from the
  console, watch the new body harvest) needs the client. That defers a stretch
  goal, where the other order defers an exercise's verification step — a smaller
  cost.

  My recommendation is server → deploy → client. Every section's subject is
  fully on screen when introduced, and the one deferral it creates is the
  smallest one available. The open placement decision is the breaking-things
  exercise: leave it at the deploy station with the stretch goal pointed at the
  client section, or move the whole exercise after the client section.

❯ one of us is confused. i think you encrypt the private key and decrypt with   
  the public. why would you encrypt the public key?                             

● The evidence is in secrix's own help from earlier in this session: -r is "an
  ad hoc public key for encryption", and -i is "the path of a private key which 
  can be used to decrypt the file". So encryption uses the public key,
  decryption uses the private key — that's the confidentiality direction, and
  it's why anyone may hold your public key but only you can read the secret. The
  private-encrypts/public-decrypts direction is signatures: signed with the
  private key so anyone with the public key can check who wrote it.

  And neither key is ever encrypted — the file in secrets/ is what gets
  encrypted. The keys are the lock and the opener.

  The wording fix I proposed stands: say "encrypt the secrets so your key can
  open them" and drop the "encrypt to your public key" idiom. Want it written
  in?
