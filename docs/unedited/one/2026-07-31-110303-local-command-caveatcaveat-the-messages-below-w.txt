Branch: create `<issue>-tutorial-5` from main. Reference:                       
`~/github/tutorial-scripts/section5/` (main.js, role.harvester.js,

FRAMING — read this first: section 5 is the tutorial's "defense"                
chapter: build a tower, `tower.repair` the closest damaged structure,           
`tower.attack` the closest hostile. The naive port is an if/else on a           
tower object in the shell — which is exactly the trap, because tower            
logic is DECISION logic and decision logic lives in the spec. Section           
5's real subject, for this project, is that the brain stops being a             
creep-only affair: the tower is the first NON-CREEP actor with policy,          
which forces the generic interpreter to prove it generalizes — new              
machine, new events, and growth in the ONLY two switches the shell is           
allowed to have (Action, TargetKind). Second architectural payoff: the          
harvester's sink list grows a third member (`spawn | extension |                
tower`), and a structure-type list hardcoded in a shell filter is               
policy wearing a trench coat — tutorial 5 moves the sink vocabulary             
into the spec where it always belonged. Third: the tutorial hardcodes           
`Game.getObjectById('TOWER_ID')`; we discover towers by structure type          
— observation, not configuration.                                               
                                                                                
## The work, in dependency order                                                
                                                                                
1. **PORT AUDIT** (tutorial-porter): diff `section5/` against the               
   current architecture and record the verdict in the session log.              
   Expected findings: role scripts — unchanged from section 4 except            
   the harvester's sink filter adds `STRUCTURE_TOWER` (becomes spec             
   data, see step 2); tower repair/attack — wholly new, belongs in the          
   spec as the first non-creep machine; `'TOWER_ID'` — becomes                  
   shell-side discovery by structure type. Note the tutorial's implicit         
   action priority: it calls `repair` then `attack`, and a tower                
   executes ONE action per tick, so attack wins when a hostile is               
   present — that priority is policy and must be explicit in the spec,          
   not an artifact of call order. Anything else section 5 does that we          
   do not — surface it before coding.                                           
                                                                                
2. **SINK VOCABULARY TO SPEC** (spec-author): the energySink target             
   kind currently means "spawn|extension with free capacity" via a              
   shell filter. Add a spec constant — an ordered list of sink                  
   structure types whose variant names are EXACTLY the Screeps                  
   `STRUCTURE_*` string values (`spawn`, `extension`, `tower`) — the            
   same literal-bridge trick as `spawnAffordBasis`, so the shell filter         
   becomes data-driven with no switch. Consequence to document in the           
   spec comment: `sinksFull` semantics widen automatically (a full              
   spawn+extensions with a hungry tower is NOT sinksFull anymore), and          
   that is the correct, intended reading — the colony feeds its guns.           
                                                                                
3. **TOWER POLICY** (spec-author, then shell-hands):                            
   - Placement: `desiredTowers` + tower offsets, reusing the                    
     `SiteOffset` pattern from extensions (spec ranks, terrain                  
     disposes). Towers need RCL 3 — placement simply fails until the            
     controller allows it; the shell keeps trying, no special casing.           
   - The tower machine: first non-creep FSM. One event per tower per            
     tick, priority explicit in the spec comment:                               
     `sawHostile > sawDamage > quiet`. States/behaviors from the fixed          
     pattern: attack→hostile, repair→damagedStructure, idle→none.               
     `Action` grows `attack`/`repair`; `TargetKind` grows `hostile`/            
     `damagedStructure`. Growing these unions is the sanctioned way to          
     extend the shell — its two switches expand, tsc proves totality,           
     and `tests/fsm-behavior.ts` moves IN THE SAME CHANGE (it rotted            
     silently once; event/state vocabulary is moving this session, so           
     it WILL need edits — budget for it).                                       
   - Shell: observe hostiles (`FIND_HOSTILE_CREEPS`) and damaged                
     structures (`hits < hitsMax`), emit the tower's event, execute the         
     brain's behavior. Tower discovery by structure type. No priority           
     logic in the shell — the event priority is spec-documented and the         
     emission order is mechanical.                                              
                                                                                
4. **DEFENSE PROOF** (telemetry + tests/integration.nix, one                    
   contract): `Memory.stats` gains `towersBuilt`, `hostiles` (live              
   count), and cumulative `towerKills` (hostile seen dead after tower           
   fire — observation of world deltas, not policy). The itest gains a           
   defense probe, and it has two hard problems to solve honestly:               
   - RCL 3 costs 45,000 controller progress — unreachable at test               
     timescales by legitimate upgrading. Decide explicitly: world               
     surgery via the server CLI (set controller level/progress in the           
     db) as TEST SETUP, clearly marked as harness, not gameplay. The            
     colony must still BUILD the tower itself afterward.                        
   - Hostiles: the private server does not conjure invaders on cue.             
     Inject a hostile NPC creep via the server CLI (db insert into              
     `rooms.objects`) — server-doctor researches the exact incantation          
     against the vendored server version before anyone writes it.               
   Then the section-5 claim, proven: hostile appears → `hostiles >= 1`          
   → tower fires → `hostiles` returns to 0 and `towerKills >= 1` —              
   unattended defense. If cheap, also assert repair: damage a structure         
   in the same surgery, watch `hits` climb back.

  before `nix flake check` / `.#itest` (boots a VM).

  scripts, never against live screeps.com.

❯ what is rcl 3 mean?                                                           

● RCL = Room Controller Level. It's the Screeps room's "tech tier." The
  controller in each room has a level (1–8) that gates what structures you're
  allowed to build.

  - RCL 1: Spawn only (where you start)
  - RCL 2: +5 extensions, +ramparts, +walls (our extension gets placed here)
  - RCL 3: +1 tower, +more extensions (this is where the tower unlocks)
  - RCL 4–8: storage, links, labs, terminal, observer, power spawn...

  You raise the RCL by having upgraders dump energy into the room controller
  (upgradeController). Each level costs more progress than the last — RCL 2
  costs 200, RCL 3 costs 45,000, RCL 4 costs 135,000.

  The itest does surgery (storage.db update via the server CLI) to jump straight
   to RCL 3 because earning 45,000 progress legitimately would take forever at
  test timescales. The colony then builds the tower itself — the surgery only
  unlocks the door, the builders still haul the 5,000 energy.

❯ how is dox-populi installed on the iso?                                       

● ${self} in the installer script. When nix builds the ISO, it interpolates
  ${self} to a nix store path containing the entire flake source. That store
  path is part of the ISO's closure — the repo source is baked into the ISO
  image itself.

  The chain:

  1. ISO build (nix build .#installer-iso): ${self} → /nix/store/...-source
  containing the repo. This path is referenced by the installer service, so it's
   pulled into the ISO's closure.
  2. Installer boots (run-vm.sh first run): the auto-install service runs
  nixos-install --flake ${self}#vm — that store path is already on the ISO, so
  nix evaluates the flake locally. It fetches flake inputs (nixpkgs etc.) from
  the internet, then downloads/builds the system closure.
  3. First boot of the installed system: dox-populi-seed service copies ${self}
  to ~/dox-populi/, git inits it, and commits — giving the user a real working
  repo.

  No git clone, no download of dox-populi itself. The source travels inside the
  ISO.
