❯ can we improve deploy-local by using native nix language                      

● Yes. The payload assembly can move out of the shell entirely:

  - For a tutorial-js section, pure Nix builds the payload at eval time:
  builtins.readDir lists the section's .js files, builtins.readFile pulls their
  text, builtins.toJSON produces {branch, modules}, and pkgs.writeText puts that
  JSON in the store.
  - For the built harness, main.js only exists after the esbuild derivation
  runs, so eval-time readFile on it would force the build during evaluation. Its
  payload instead becomes a small runCommand that wraps ${main}/main.js into
  the same JSON shape at build time.

  The shell script then shrinks to signin plus one curl of a ready-made payload
  file. deploy-local stays one app: the argument names a section (nix run 
  .#deploy-local -- section1), no argument means the harness build. The
  name-to-payload lookup in the script is generated from builtins.readDir 
  ./tutorial-js, so adding tutorial-js/section2 later needs no flake edit.

  Two consequences to accept:

  1. The argument names a section known at eval time. Pointing the app at an
  arbitrary directory at runtime is out of this design.
  2. tutorial-js has to be tracked by git — a flake's source is the git tree, so
  untracked files are invisible to readDir. A git add tutorial-js is needed
  before it works.

  Want me to write it this way?
