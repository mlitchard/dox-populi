❯ what does this mean 'rewriting the spec so a tower is a sink whenever it's    
below 1000'                                                                     

● Straight talk, no jargon.

  "Sink" = a place creeps deliver energy to. Every tick, a creep carrying energy
   asks the brain "where do I dump this?" The answer comes from a filter over
  spawn + extensions + towers: which of these can still accept energy? Whatever
  passes the filter is in the delivery set; whatever doesn't is invisible — no
  creep will ever walk energy to it.

  Current law (what I wrote after your ruling): a tower passes that filter only 
  when the latch is open — energy dropped below 500 and hasn't hit 1000 yet. So:

  - Tower at 990: latch closed → tower fails the filter → invisible to every 
  creep. Nobody will ever deliver those last 10 energy. Forever. That's your
  "creeps stopped giving energy to the tower."

  Proposed law: a tower passes the filter whenever energy < 1000 — same rule as
  a spawn or extension ("has room? deliver."). So a 990 tower is a normal
  delivery target and gets topped back to full — which is exactly what the raid
  gate needs to open.

  The latch doesn't disappear — it changes jobs. Instead of deciding whether the
   tower gets fed, it decides how urgently: when energy drops below 500, the
  tower jumps to the front of the delivery line, ahead of spawn and extensions,
  until it reads 1000 again. Above 500, it's just one more sink in the rotation,
   no special treatment.

  One sentence: today a 990 tower gets nothing; under the fix it gets casual 
  top-ups, and only a sub-500 tower gets emergency priority.

  That's the whole change. Do I write it?

  The setup

  Agents are markdown files with YAML frontmatter, one per agent:

  - Project agents: .claude/agents/*.md (this repo has spec-author, shell-hands,

  - Personal agents: ~/.claude/agents/*.md (all your projects)

  You are the Paradox spec author for dox-populi...

  The model field — that's your lever

  ┌──────────────┬──────────────────────────────────────────────────────────┐
  │    Value     │                         Meaning                          │
  ├──────────────┼──────────────────────────────────────────────────────────┤
  │ inherit      │ whatever model the main session runs (what yours all do  │
  │              │ now)                                                     │
  ├──────────────┼──────────────────────────────────────────────────────────┤
  │ opus         │ Opus 4.6 — heavy reasoning                               │
  ├──────────────┼──────────────────────────────────────────────────────────┤
  │ sonnet       │ Sonnet 4.6 — strong, cheaper                             │
  ├──────────────┼──────────────────────────────────────────────────────────┤
  │ haiku        │ Haiku 4.5 — fast, cheap                                  │
  ├──────────────┼──────────────────────────────────────────────────────────┤
  │ full model   │ e.g. claude-haiku-4-5-20251001 — pin exactly             │
  │ ID           │                                                          │
  └──────────────┴──────────────────────────────────────────────────────────┘

  How work lands on them

  1. Auto-delegation — I read the description field and route matching tasks
  there myself. That "Use it PROACTIVELY whenever..." phrasing in spec-author is
   doing exactly that job. Sharper description = better routing.
  2. Explicit — you say "have spec-author do X" or I invoke it via the Agent
  tool.
  3. /agents — interactive manager: create, edit, pick tools and model from a
  menu instead of hand-writing frontmatter.

  The play for THIS repo, if you want my counsel

  wrong is expensive.
