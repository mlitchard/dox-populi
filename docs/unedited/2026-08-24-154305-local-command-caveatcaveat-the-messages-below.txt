● X is programs. The space I sample from when you say "write me creep logic in
  JavaScript" is the space of plausible programs — everything that parses, runs,
  and looks like code a competent person would write. That space is enormous,
  and the programs that are actually right occupy a sliver of it. My failure
  mode as a generator is exactly that gap: I am very good at producing the
  plausible, and plausibility correlates weakly with correctness. Raw JavaScript
  does nothing to close the gap — it accepts anything, so every branch I emit
  is a claim with no check behind it, and my errors don't look like errors. They
  look like code.

  Here's my own assessment of what Paradox did to that, from working this
  codebase:

  First, it shrinks what I'm allowed to say. In dox/creeps.dox I can only
  express decision structure — unions, constants, states, events, transitions. I
  cannot express a side effect, an API call, a clever shortcut. The degrees of
  freedom collapse from "any program" to "which transition fires for which
  state-event pair." Most of the ways I could be wrong in raw JS are not
  writable in the spec language at all.

  Second, it makes my most common error unwritable-without-detection. My
  characteristic bug is the unconsidered case: the event arriving in a state I
  didn't think about, the branch I never wrote because nothing prompted me to
  think of it. In raw JS that omission is silent — the code runs and does
  something. Paradox FSMs are total: every state crossed with every event must
  have an explicit transition, self-loops included. The case I failed to
  consider stops being a silent hole in the behavior and becomes a named cell in
  a failing check. The checker doesn't make me smarter; it makes my omissions
  loud.

  Third, the feedback is shaped the way I use feedback best. When raw JS is
  wrong, the signal comes back late and vague — a creep idles, telemetry looks
  off, and I'm left interpreting symptoms, which is where I start guessing. When
  a spec is wrong, paradox check names the violated property at write time.
  Short loop, precise signal. I iterate extremely well against a crisp rejection
  and extremely poorly against "it seems not to work." Paradox converts the
  second kind of feedback into the first.

  Fourth, I never transcribe the decisions into imperative code — so I can't 
  botch the transcription. The running TypeScript is emitted by paradox 
  generate. A whole class of my errors — right decision table, wrong nesting of
  the if/else that was supposed to implement it — is gone because that
  translation step was taken away from me. The only code I write by hand is the
  shell: observation and API calls, with tsc --strict holding the boundary
  between what I wrote and what was generated.

  Fifth, the spec is one artifact I can hold whole. Decision logic in raw JS
  diffuses across files, and my coherence degrades with distance — each local
  edit plausible, the global behavior drifting. The spec concentrates every
  policy decision in one table, and every edit to it is re-checked as a whole,
  not just at the point of change.

  And the honest boundary, because your laws demand it and it's true: Paradox
  never knew what the bot should do. I can write a total, consistent FSM that is
  verified and wrong — post 4 exists because I did. The checks close the gap
  between what I meant and what I wrote. The gap between what I wrote and what
  was needed stayed yours.

  Which is the inter-relation you named, stated flat: I have breadth without
  guarantees; Paradox has guarantees but a spec doesn't write itself cheaply —
  before agents, filling out that structure was expert labor. I make Paradox
  cheap. Paradox makes me checkable. Neither claim runs the other direction
  alone.

  The Session

  The transcript behind this post is the delivery fight: July 26th, the session
  where the project learned to install itself for people who have never heard of
  nix. My messages are in bold, verbatim, typos and all. The assistant's output
  is trimmed to what matters; the full transcript ships with this series'
  context sources.

  It started with the assistant drifting toward a host that has nix installed.

  ▎ so you are giving up on the requirements? i want non-nix users to have 
  ▎ access.

  The requirement held. The assistant offered two paths; publishing a built ISO
  won. run-vm.sh learned a resolution order — an ISO beside the script, a
  maintainer build in result/iso/, or a download — and the host's dependency
  list stayed at qemu, tmux, curl.

  The first "done" didn't survive contact. The assistant announced "Validated:
  installer-iso evaluates, isoImage.isoName = dox-populi-installer.iso" — while
  the nix eval above that claim had printed
  nixos-minimal-26.05.20260722.b3fe958-x86_64-linux.iso. My terminal disagreed
  twice:

  ▎ this failed [nix-shell:~/gitlab/dox-populi]$ INSTALL=1 ./run-vm.sh
  ▎ …
  ▎ error: installer ISO not found: 
  ▎ /home/mlitchard/gitlab/dox-populi/dox-populi-installer.iso

  Forced back to the source, the assistant read the nixpkgs iso-image modules
  and found the cause: isoImage.isoName has been a dead alias since NixOS 25.05.
  The fix was image.baseName = lib.mkForce "dox-populi-installer", and the
  verdict is on the record: nix eval .#packages.x86_64-linux.installer-iso.name
  → "dox-populi-installer.iso". The same pasted terminal exposed a second bug:
  tmux spawns sessions with its own environment, so the dev shell's qemu wasn't
  on PATH inside the session. run-vm.sh now resolves qemu to an absolute path up
  front and fails fast if it's missing — you can't assume your caller's
  environment survives into a detached session.

  The installer itself failed next, and I said so without ceremony:

  ▎ i cannot nixos-install in the vm and i cannot copy paste you have failed in 
  ▎ the task

  The response was evidence, not apology: console capture, journalctl over the
  serial line, dmesg, a manual mount. Root cause: right after mkfs.ext4, a bare
  mount races udev and filesystem autodetection fails. The installer gained
  udevadm settle and an explicit mount -t ext4 — a timing race seen once on a
  live console, baked into the installer permanently.

  When the assistant ran out of knowledge, it did not run out of suggestions.
  That got stopped:

  ▎ stop guessing, if you are out of ideas say so. stop guessing.
  ▎ [dev@dox-populi:~/dox-populi]$ echo $STEAM_SCREEPS_DIR
  ▎ /home/dev/screeps
  ▎ …
  ▎ error: bundled node not found at /home/dev/screeps/resources/node

  It stopped. It read the server's actual code and found the real bug: the app
  runs $STEAM_SCREEPS_DIR/resources/node, so the variable must point at the
  game's server subdirectory. The fix landed in vm/module.nix with the reason in
  a comment.

  Then the security ruling, which I had to make twice:

  ▎ they are going to prvide their own keys, dont hardcode a particular key

  ▎ we will provide tools and instructions to use secrix to encrypt/decrypt, but
  ▎ they provide keys. this is not optional. this is required. i never told you
  ▎ this was optional. you are to stop making inferrence

  The hardcoded key path came out of flake.nix. No key ships with the project;
  you bring your own.

  And at the end, a live error became a design obligation:

  ▎ this needs to be handled in the flake. '[dev@dox-populi:~/dox-populi]$ nix 
  ▎ run .#server … SCREEPS_IDENTITY: secrets/STEAM_TOKEN exists — set 
  ▎ SCREEPS_IDENTITY to the key it is encrypted to'

  The identity lookup moved out of instructions and into all three apps in
  flake.nix: SCREEPS_IDENTITY → $WORKDIR/identity → ~/work/identity, failing
  with placement instructions when no key is found. Verified by nix eval on all
  three apps before the session closed.

❯ let's talk about the 32G, I made this footprint for the sake of speedy builds 
  on my machine, but I doubt this is a minimum requirement. give me a plan of   
  action to determine minimal requiements?                                      

● Good instinct — 32G is a comfort figure, not a floor, and right now the
  exercise page asserts it to every reader as if it were load-bearing. Here's
  the plan of action, and the pleasant surprise is that your
  20-hardware-contract branch already built most of the apparatus for it.

  1. Define "minimum" before measuring anything. Two profiles, because they'll
  have different floors:

  - Run floor — what the post-zero exercise needs: boot the installed system,
  server starts, world ticks, deploy works, a creep harvests, curl answers. This
  is exactly what the itest already verifies.
  - Work floor — what later posts need: edit the spec inside the VM, rebuild
  (paradox generate, tsc, esbuild), redeploy. Nix builds are the likelier memory
  hog, and the ISO's pre-built devShell doesn't exempt rebuilds.

  The exercise page needs the run floor; the equipment section of later posts
  needs the work floor.

  2. Measure before you bisect. One instrumented run at 32G: boot, run the full
  workflow, and record peak memory — memory.peak from the screeps service's
  cgroup, /proc/meminfo MemAvailable low-water, dmesg for OOM, and actual tick
  time against the configured tickMs. Same for a build. That gives you a bracket
  for free instead of six blind runs — if the server peaks at 5G, you start the
  search at 6, not 16.

  3. Bisect with the itest as the judge. This is where the branch pays off:
  tests/integration.nix now takes memorySize and cores as arguments from the
  hardware contract. Sweep descending memory — the itest either passes or it
  doesn't. A pass only counts clean: no OOM kills in dmesg, no swap thrash, tick
  time within tolerance of the 32G baseline — a world that ticks at triple the
  configured tick isn't "working," it's dying slowly. The floor is the lowest
  clean pass plus safety margin (say, the next step up).

  4. Same sweep for cores, coarser: 8 → 4 → 2. The server runs several child
  processes; tick time is again the tell.

  5. Work-floor pass separately: at the candidate run floor, do the
  representative rebuild inside the VM. If it OOMs, walk memory up until it
  completes; that number is the work floor.

  6. Land the answers where the branch wants them: the floors become constants
  in the hardware attrset alongside the speedy defaults — your 32G stays as the
  default for your machine, the measured floor goes into run-vm.sh's env-knob
  documentation ("MEM default 32G; floor NG") and into the exercise text as the
  honest requirement. One nix run .#gen-run-vm propagates it. The itest keeps
  running at the floor, not the comfort figure — then every CI run re-certifies
  the minimum claim instead of just your workstation's convenience.

  Two costs to own before you start: each bisection step boots a full itest VM —
  that's the expensive check, sequential, minutes apiece, so the whole sweep is
  an afternoon of machine time; and the floor you'll certify is a fresh-world
  floor — the LokiJS world db grows with a long-running world, so the exercise
  number is honest for the reader's first boot, and the growth caveat is one
  sentence, no measurement needed.

  Say the word on any piece you want executed — the instrumented 32G baseline
  run is the natural first move, and it's a single itest with monitoring on.
