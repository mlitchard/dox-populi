  ---
  The Abstraction

  Here's the machine I'm extracting. dox-populi isn't a Screeps project that
  happens to use Paradox. It's an instantiation of a five-layer engine-client 
  architecture where Paradox + nix do the heavy lifting and the engine is a
  parameter.

  The Five Layers

  Layer: 1. Spec
  What it is: .dox files: unions, types, constants, FSMs. Paradox check + Z3
    verify structural properties (determinism, reachability, deadlock freedom,
    complete event coverage, liveness).
  Engine-specific?: No. Same .dox, same checks, any engine.
  ────────────────────────────────────────
  Layer: 2. Codegen
  What it is: paradox generate --{lang} emits idiomatic brain code: types,
    validators, transition functions.
  Engine-specific?: No. Just change the --target flag. Rust already works.
  ────────────────────────────────────────
  Layer: 3. Shell
  What it is: The "hands." Observes the engine world, emits one spec event per
    entity per tick, receives a state, executes the engine action.
  Engine-specific?: Yes. This is the only layer that touches the engine API.
  ────────────────────────────────────────
  Layer: 4. Type bridge
  What it is: Engine-specific ambient types the shell compiles against.
    (typed-screeps for Screeps, godot-rust/gdext for Godot.)
  Engine-specific?: Yes. Vendored or declared as a flake input.
  ────────────────────────────────────────
  Layer: 5. Nix pipeline
  What it is: spec-check → generate → typecheck/compile → bundle → deploy → 
    itest. Each step is a pure nix derivation.
  Engine-specific?: Shape is reusable. Concrete steps are engine-specific
    (esbuild vs cargo, HTTP deploy vs file copy, etc.)

  The Shell Boundary Contract

  This is the critical interface — the seam between engine-agnostic and
  engine-specific:

  observe(world) → Event        -- engine-specific: read game state, classify it
  transition(state, event, ctx) → State   -- engine-agnostic: generated brain
  execute(state, world) → ()    -- engine-specific: call engine API

  In dox-populi today, that's:
  - emitEvent(creep, spawn): CreepEvent — reads Screeps store, classifies as
  storeEmpty|storeFull|spawnFull|tick
  - harvesterTransition(state, event, ctx) — generated, pure, no Screeps API
  - switch(target) — calls creep.harvest(), creep.moveTo(), creep.transfer()

  In a Godot+Rust instantiation, it'd be:
  - fn emit_event(node: &CharacterBody3D, world: &World) -> CreepEvent — reads
  Godot node properties
  - fn harvester_transition(state, event, ctx) -> HarvesterTransitionResult —
  generated by paradox generate --rust, identical structure
  - match target { ... } — calls gdext: node.move_and_slide(), node.look_at(),
  etc.

  The Godot+Rust Instantiation

  dox/game.dox                      ← same Paradox spec language
    ↓ paradox check + Z3            ← same verification
    ↓ paradox generate --rust       ← already works today
  generated/mod.rs                  ← enums, structs, match-based transitions
    +
  shell/lib.rs                      ← gdext: observe → event → transition →
  execute
    ↓ cargo build (with godot-rust/gdext crate)
  target/libgame.so                 ← .gdextension native library
    ↓ copy into Godot project
  project.godot                     ← Godot loads the extension
    ↓ godot4 --headless --scene test.tscn
  itest                             ← NixOS test: boot → run scene → poll stats
  file

  The flake.nix shape maps directly:

  ┌─────────────────────────────┬───────────────────────────────────────────┐
  │   dox-populi (Screeps/JS)   │          dox-godot (Godot/Rust)           │

  └─────────────────────────────┴───────────────────────────────────────────┘

  What's Truly Reusable (the "kit")

  1. The spec language and its verification. Paradox + Z3 + the Machine type.
  Write once, generate anywhere. The FSM checks (determinism, reachability,
  deadlock freedom) are engine-independent mathematical properties.
  2. The brain/hands split as an architectural law. Not "a good idea" — a
  constraint enforced by the directory structure and the build pipeline. The
  generated code has no engine imports. The shell has no decision logic. The
  checkers enforce both directions.
  3. The nix pipeline shape. Five pure derivations chained: verify → generate →
  compile → bundle → test. Engine-specific glue fills in what each step does,
  but that they exist and how they compose is the reusable skeleton.
  4. The agent decomposition. spec-author is engine-agnostic — it works on .dox.
   shell-hands and server-doctor get engine-specific system prompts. The pattern
   of splitting agents by architectural layer transfers directly.
  5. The evolution framework. The hybrid mutator you've designed is
  engine-agnostic precisely because of the brain/hands split. The genome mutates
   the spec → Paradox regenerates → the fixed shell interprets → fitness comes
  from telemetry. The shell doesn't change per mutation, so novel states from
  mutants work as long as the shell is a generic FSM interpreter. That's the
  prereq refactor you already identified.

  What Doesn't Transfer (engine-specific work)

  - The shell itself. Every engine has its own API, its own observation model,
  its own action vocabulary. You write a new shell/lib.rs (or shell/main.gd, or
  shell/main.lua for Defold, or...).
  - The type bridge. Godot needs gdext bindings, not typed-screeps. This is a
  flake input, not hand-written.
  - Server vendoring. Each engine has its own runtime. Godot 4 is in nixpkgs.
  Some engines (Defold, Love2D) are trivial to vendor. Some (Unity) are a
  nightmare.
  - Deploy and test mechanisms. File copy vs HTTP POST vs CLI push. Headless
  mode vs API poll.

  The Real Pitch

  You're not building "a Screeps bot framework." You're building a spec-driven 
  client delivery system where:

  - The LLM authors the spec (the .dox), not the code
  - The checkers (Paradox + Z3 + target-language typechecker) verify the spec,
  not the human
  - Nix makes the whole pipeline reproducible and pure
  - The engine is a swappable parameter behind a fixed shell boundary

  A Godot project using this method would get: verified FSMs in Rust, generated
  from the same Paradox spec language, built and tested in a pure nix pipeline,
  with the same agent decomposition, and — when you build the orchestrator — the
   same evolutionary tournament mutating strategies across Godot game scenes.

  The Screeps tutorial is the proof of concept. The abstraction is the product.

● Right. Let me be precise about what makes Screeps special here, because it's
  not just "a game" — it's a very specific architecture that most games don't
  have.

  What Screeps actually is (the rare part)

  Screeps is a code-execution runtime with an API intake. You push JavaScript to
   an HTTP endpoint, the server evaluates it every tick against a shared world,
  and your code's only interface to the world is a fixed API surface
  (Game.creeps, creep.harvest(), Memory, etc.). You never touch the rendering.
  You never handle input. The game is the code.

  That's three properties stacked together:

  1. Server-side code execution — the engine runs YOUR code, not just
  data/config
  2. API-based code delivery — push code over HTTP, no build step on the server
  side
  3. Fixed API surface — the set of observations and actions is defined by the
  engine, not you

  Why Godot doesn't fit

  Godot is the opposite of all three:

  - You build the game, including the rendering, physics, input handling —
  everything
  - There's no "push code to a running engine" — you ARE the engine
  - There's no fixed API surface to observe/act against — you define the API

  So the brain/hands split still works conceptually in Godot, but the shell
  wouldn't be a thin adapter against a foreign API. You'd be writing the entire
  game and then constraining part of it to be spec-driven. That's a different
  value proposition — you're not delivering a client to someone else's engine,
  you're building an engine that happens to use Paradox internally.

  What you actually need

  An engine/platform that:

  1. Accepts code at runtime via some delivery mechanism (API, file watch,
  plugin load)
  2. Provides a fixed world model you observe and act on — you don't define the
  world, you react to it
  3. Has an active game/simulation with other players or meaningful dynamics —
  not a sandbox you build from scratch

  Screeps is the gold standard of this. The question is: what else fits?

  ---
  ComputerCraft (CC: Tweaked) — the mapping

  What it is

  A Minecraft mod that adds programmable computers and turtles. Turtles are
  robots that move through the 3D Minecraft world — digging, placing blocks,
  attacking mobs, managing inventory, crafting. You program them in Lua. The mod
   is actively maintained (78M+ downloads), runs on Fabric and Forge, and has a
  massive community.

  Why it fits the pattern

  Fixed API surface — The turtle API is tight and well-defined:

  ┌─────────────────┬───────────────────────────────────────────────────────┐
  │    Category     │                       Functions                       │
  ├─────────────────┼───────────────────────────────────────────────────────┤
  │ Movement        │ forward, back, up, down, turnLeft, turnRight          │
  ├─────────────────┼───────────────────────────────────────────────────────┤
  │ Block           │ dig/digUp/digDown, place/placeUp/placeDown            │
  │ interaction     │                                                       │
  ├─────────────────┼───────────────────────────────────────────────────────┤
  │ Sensing         │ detect/detectUp/detectDown,                           │
  │                 │ inspect/inspectUp/inspectDown                         │
  ├─────────────────┼───────────────────────────────────────────────────────┤
  │ Inventory       │ select, getItemCount, getItemSpace, drop, suck,       │
  │                 │ transferTo, craft                                     │
  ├─────────────────┼───────────────────────────────────────────────────────┤
  │ Combat          │ attack/attackUp/attackDown                            │
  ├─────────────────┼───────────────────────────────────────────────────────┤
  │ Fuel            │ getFuelLevel, getFuelLimit, refuel                    │
  ├─────────────────┼───────────────────────────────────────────────────────┤
  │ Peripherals     │ modem, monitor, speaker, disk, inventory              │
  └─────────────────┴───────────────────────────────────────────────────────┘

  Every function returns boolean, string|nil — success/failure with reason.
  That's more structured than Screeps, where you get numeric error codes.

  Server-side code execution — The Lua runs inside the Minecraft server's
  CC:Tweaked runtime. The turtle exists in the actual Minecraft world, affected
  by physics, other players, mobs.

  Active game with dynamics — Minecraft is the dynamics. Other players, mobs,
  world generation, redstone — you're programming agents in a living world.

  The brain/hands split maps cleanly

  The .dox spec would define:

  union TurtleState
    mining
    returning
    depositing
    exploring
    refueling

  union TurtleEvent
    inventoryFull
    inventoryEmpty
    fuelLow
    blockDetected
    pathClear
    atChest
    tick

  The shell would be a Lua script that:
  1. Observes: turtle.inspect(), turtle.getFuelLevel(), turtle.getItemCount() →
  emits a TurtleEvent
  2. Transitions: calls the generated brain function (pure, no Minecraft API)
  3. Executes: turtle.dig(), turtle.forward(), turtle.drop() based on the target
   state

  The critical difference from Screeps

  Screeps calls your loop() every tick automatically. CC:Tweaked doesn't — your 
  code IS the event loop. The turtle runs your Lua program continuously, and you
   write the while true do ... end yourself. This is actually simpler for the
  shell — you control the cadence, you decide when to observe and act.

  Two architectural options

  Option A: All-Lua (parallel to Screeps' all-JS)

  dox/turtle.dox                   <- Paradox spec
    | paradox check + Z3
    | paradox generate --lua       <- needs new backend (Paradox author will
  write it)
  generated/brain.lua              <- tables, functions, match-based transitions
    +
  shell/main.lua                   <- observe turtle state → event → transition
  → execute action
    | deploy to turtle filesystem
  turtle in Minecraft               <- runs the program

  Self-contained. Everything runs on the turtle. No external dependencies. This
  is how CC:Tweaked is normally used.

  Option B: WebSocket bridge (brain runs externally)

  CC:Tweaked has built-in WebSocket support (http.websocket()). Community
  projects already do this — https://github.com/EvanA4/RCturtle,
  https://github.com/runi95/turtle-control-panel,
  https://github.com/wwaaijer/cc-socket-server.

  dox/turtle.dox                   <- Paradox spec
    | paradox generate --typescript (or --rust, --haskell — any existing
  backend)
  generated/brain.ts               <- uses an EXISTING codegen target
    +
  brain-server/                    <- external process, serves brain decisions
  via websocket
    +
  shell/client.lua                 <- thin stub: connect to websocket, send
  observations, receive commands
    | deploy to turtle filesystem
  turtle in Minecraft               <- relays observations, executes received
  commands

  No new Paradox backend needed. Brain can be computationally heavy. Evolution
  framework runs externally. BUT: requires network between MC server and brain
  server.

  The testing story

  This is where it gets interesting — three layers:

  1. CraftOS-PC — native C++ emulator, 90% faster than in-game. Has headless

  https://github.com/MCJack123/craftos2-turtle, but it's rudimentary (3

  2. HeadlessMC — headless Minecraft launcher for CI/CD. Can run an actual

  3. nix-minecraft — NixOS module for declarative modded Minecraft servers.

  The friction points

  1. Lua codegen. Paradox doesn't have --lua yet. The Paradox author will write
  it — Lua is simple (tables, strings, functions, no static types), so the
  generated code would be runtime-validated like TypeScript validators minus the
   type annotations. But it's work.
  2. Integration testing is heavier. A headless Minecraft server is a JVM
  process with a full world. CraftOS-PC is lightweight but can't simulate a real
   world. The itest would be slower and more resource-intensive than Screeps'
  lightweight Node.js server. The NixOS VM test would need more memory and time.
  3. No tick model. Screeps' tick gives you a clean discrete-time model: one
  loop() per tick, one event per entity per tick. CC:Tweaked is continuous — you
   control the loop, and actions take variable time (movement takes a few ticks,
   turtle.dig() depends on block hardness). The FSM still works, but the shell
  needs to handle timing/yields explicitly.
  4. 3D vs 2D. Screeps rooms are 2D grids. Minecraft is 3D. Navigation is
  harder. The spec needs a richer spatial vocabulary (up/down/forward/backward
  vs just x/y).
  5. World state is opaque. Screeps gives you Game.rooms, Game.creeps — full
  world state every tick. CC:Tweaked gives you only what the turtle can sense:
  one block ahead (inspect()), one block above, one block below. No global map.
  The turtle is blind beyond its immediate surroundings. This changes the FSM
  design — you need exploration/mapping states, not just task states.

  The verdict

  CC:Tweaked maps well to the abstraction. The fixed API surface, server-side
  execution, and active world dynamics are all there. The brain/hands split
  works naturally. The nix pipeline shape transfers (nix-minecraft exists). The
  community is huge.

  The two real questions:

  1. Option A or Option B? Option A (all-Lua) is the clean parallel to Screeps.
  Option B (websocket bridge) is more powerful and skips the Lua backend work,
  but adds a network dependency and is architecturally different from "push one
  artifact to the engine."
  2. Is the testing story pure enough? The Screeps itest is a 4GB VM running a
  lightweight Node server. The CC:Tweaked itest would be a VM running a JVM
  Minecraft server with Fabric and mods. Heavier, but nix-minecraft makes it
  declarative. The question is whether nix flake check can boot a headless
  Minecraft server, place a turtle, load code, and verify behavior in reasonable
   time.

  What's your instinct — Option A or B? And how much do you care about the itest
   being fast vs. being real?
