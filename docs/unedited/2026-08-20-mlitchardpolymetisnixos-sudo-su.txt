❯ how do I safely upgrade to 26.05                                              

● First, the cross-examination you knew was coming: you upgrading the whole 
  system for one package? 'Cause unstable.grok-build gets you the toy with a
  one-line blast radius. A release upgrade moves every package and every NixOS
  module on the machine. If the answer is "it's time anyway" — fine, that's a
  real answer. Here's how you do it without betting the machine.

  NixOS makes this about as safe as upgrades get, because every generation is
  kept and bootable. The discipline is: commit → retarget → build → test → 
  switch, in that order.

  1. Commit first. Your rebuild already ratted you out — "uncommitted changes."
  Commit the working 25.11 state so the rollback of your config is git revert,
  not archaeology.

  2. Retarget the pin deliberately. Your input is:

  nixpkgs.url = "https://flakehub.com/f/NixOS/nixpkgs/0";

  That /0 constraint means "latest anything" — a bare nix flake update decides
  your release for you. Pin it on purpose:

  nixpkgs.url = "https://flakehub.com/f/NixOS/nixpkgs/0.2605.*";

  then nix flake update nixpkgs. If FlakeHub rejects 0.2605.*, 26.05 ain't
  published there yet and this whole plan waits — the resolver will tell you
  honestly.

  3. Read the receipts. The https://nixos.org/manual/nixos/stable/release-notes
  — breaking changes, renamed options. Two minutes of reading beats an hour of
  eval errors. And hear me on this: do NOT touch system.stateVersion. It stays
  at whatever it was when the machine was born. That's not a version number,
  it's a birth certificate.

  4. Build without activating.

  nixos-rebuild build --flake .#Polýmētis

  Eval errors, renamed options, broken packages — they all surface here, while
  your running system stays untouched.

  5. Test without committing to it.

  nixos-rebuild test --flake .#Polýmētis

  Activates the new system but writes no boot entry. Something's wrong? Reboot
  and you're back on 25.11 like it never happened.

  6. Then, and only then:

  nixos-rebuild switch --flake .#Polýmētis

  And even now you're not trapped — old generations sit in the boot menu, and
  nixos-rebuild switch --rollback walks it back.

  Housekeeping while you're in there: once pkgs is 26.05, grok-build works bare
  — no unstable. prefix needed. And you might check whether nixpkgs-2411 and the
   unstable input still earn their keep, but that's a separate trial for a
  separate day.

  So — which road? One-line unstable.grok-build today, or the full 26.05
  ceremony?

● Good news dressed up as a fire alarm. Read the confession in the log: "failed 
  to initialize NVML: Driver/library version mismatch."

  Here's what happened. Your running kernel is still holding the old NVIDIA
  kernel module — loaded at boot, been up over a week. The test activation just
  swapped the userspace over to 26.05's driver. New library, old module, and
  NVML says "who are you?" The CDI generator dies on contact. You cannot
  hot-swap an NVIDIA kernel module under a live display server — this failure is
   baked into live-switching across a driver bump. It is not evidence your 26.05
   config is broken. Exit status 4 = "switched, but some units failed" — and
  only that one unit failed.

  So the trial's actually going well: eval passed, build passed, everything
  except the one service that physically cannot pass without a reboot came up.
  This is exactly the mismatch a fresh boot resolves — kernel module and
  userland loaded from the same generation, in matching versions.

  Your move, and it's a fork:
